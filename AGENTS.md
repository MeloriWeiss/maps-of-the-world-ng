# AGENTS.md

## Общие правила

- Общайся с пользователем на русском языке.
- Не изменяй код, который не относится к текущей задаче.
- Сохраняй обратную совместимость, если явно не сказано обратное.
- Не добавляй зависимости без необходимости.
- Не запускай destructive-команды и не удаляй данные без подтверждения.

## Локальная память проекта

- В начале работы прочитай `.codex/memory.md`, если файл существует.
- Не перечитывай `.codex/memory.md`, если она уже была прочитана в текущей сессии и пользователь не просил проверить её повторно.
- Актуализируй `.codex/memory.md` только по явной команде пользователя, обычно один раз в конце рабочей сессии.
- Не сохраняй в локальной памяти пароли, токены, приватные ключи и другие секреты.
- Проверяй сведения из локальной памяти по текущему коду, если они могли устареть.

## Экономия контекста

- Для небольших задач не составляй отдельный план и не отправляй промежуточные сообщения, если работа занимает меньше минуты и не требует длительных команд.
- Исследуй только файлы и подсистемы, необходимые для текущей задачи; не проверяй смежный функционал без причины.
- Не повторяй в итоговом ответе подробности, уже известные пользователю; сообщай результат, существенные решения и статус проверок.
- Выбирай проверки пропорционально риску и масштабу изменений. Не запускай полные build, lint и test для документационных или небольших конфигурационных изменений, если они не затрагивают исполняемый код.
- Полные проверки запускай по явной просьбе пользователя, перед релизом или когда без них нельзя надёжно подтвердить корректность изменений.

## Вёрстка

- Всегда используй CSS-переменные для любых цветов в стилях и коде интерфейса; не добавляй литералы `#...`, `rgb(...)`, `rgba(...)`, `hsl(...)` и именованные цвета вне файла палитры `apps/web/src/styles/variables.scss`.
- Сначала выбирай существующую семантическую переменную по назначению (`--text-*`, `--bg-*`, `--border-*`, `--btn-*` и т. п.), а не по визуальному сходству значения в одной теме.
- Если подходящей семантической переменной нет, создай новую с окончанием `-color` и задай её для каждой поддерживаемой темы: `light`, `dark`, `steampunk` и `neon-sunset`.
- Общие палитровые переменные (`--red-color`, `--green-color` и подобные) используй напрямую только когда цвет имеет неизменный семантический смысл во всех темах; для тематически изменяемого оформления создавай семантический токен.
- Прозрачность, градиенты, тени и вычисляемые оттенки также строй от CSS-переменных, например через `rgb(from var(--...-color) r g b / 40%)`.
- При изменении цветов проверяй затронутый интерфейс во всех поддерживаемых темах.

## Nx

- Для библиотек в `libs/api/<library>` используй имя Nx-проекта `api-<library>`, а для библиотек в `libs/web/<library>` — `web-<library>`; применяй префикс ко всем платформенным библиотекам, а не только при коллизиях.
- В путях каталогов и TypeScript-алиасах не повторяй область: используй `libs/api/shared` и `@wm/api/shared`, а не `libs/api/api-shared` и `@wm/api/api-shared`.
- Общие для API и web библиотеки размещай в `libs/shared` и именуй без платформенного префикса.
- После добавления или переименования библиотеки запускай `yarn lint:workspace`, который проверяет соглашение автоматически.

## TypeScript

- Используй строгую типизацию.
- Не используй `any`.
- Не применяй type assertions без необходимости.
- Предпочитай ранние возвраты глубокой вложенности.
- Публичные методы должны иметь понятные названия.
- Повторяющуюся логику выноси в отдельные функции или сервисы.
- Приватные переменные создавай с помощью нативного синтаксиса `#`, а не через ключевое слово `private`.
- Не пиши возвращаемый тип функции, если она ничего не возвращает.

- Не обращайся к DOM напрямую, если задачу можно решить средствами Angular.
- Подписки должны корректно уничтожаться.
- Соблюдай существующее разделение feature/data-access/ui.
- Не вызывай функции и сложные геттеры в шаблоне, а по возможности полностью откажись от этого.

- Если создаёшь полноценный раздел приложения, который имеет несколько страниц и маршрутов, то выноси его роутинг в отдельный файл и сохраняй в соответствующей nx-библиотеке.

## SEO

- Считай SEO обязательным требованием для всех публичных индексируемых страниц.
- Перед изменением страницы определи, должна ли она индексироваться. Для личных кабинетов, редакторов, служебных, поисковых и пользовательских страниц с приватными данными используй `noindex`, если явно не указано обратное.
- Для каждой индексируемой страницы обеспечивай уникальные и содержательные `title` и `meta description`, корректный canonical URL, один логически главный `h1`, последовательную иерархию заголовков, человекочитаемый URL и семантическую HTML-разметку.
- Для динамических страниц формируй `title`, `meta description`, canonical, Open Graph и Twitter Card из данных страницы с безопасными значениями по умолчанию.
- Для страниц, которыми могут делиться пользователи, добавляй Open Graph и Twitter Card.
- Для релевантных страниц добавляй валидные структурированные данные Schema.org в формате JSON-LD. Не указывай в них сведения, которых нет в видимом содержимом страницы.
- Содержательные изображения должны иметь осмысленный `alt`, декоративные — пустой `alt`.
- Не размещай важный индексируемый текст только внутри `canvas`, фонового изображения или клиентской интерактивности без доступного HTML-эквивалента.
- Новые публичные страницы должны быть доступны через обычные ссылки `<a>` без обязательного выполнения пользовательского действия.
- Не создавай дубли страниц. Для фильтров, сортировки, пагинации и query-параметров явно определяй стратегию canonical и индексации.
- При удалении или изменении публичного URL сохраняй старый адрес через постоянный редирект, если у страницы есть замена.
- Для публичных индексируемых страниц учитывай SSR, SSG или prerender и не рассчитывай исключительно на выполнение JavaScript поисковым роботом.
- При изменении публичных маршрутов проверяй и при необходимости обновляй `robots.txt`, XML sitemap, canonical URL и правила редиректов.
- Не блокируй в `robots.txt` ресурсы, необходимые для корректного отображения индексируемых страниц.
- Не добавляй `noindex`, canonical или structured data глобально без проверки влияния на существующие маршруты.
- Следи за Core Web Vitals: не ухудшай LCP тяжёлыми изображениями и блокирующими ресурсами, предотвращай CLS, ограничивай тяжёлую работу в основном потоке и используй lazy loading только для содержимого вне первого экрана.
- SEO не должно ухудшать доступность, безопасность или корректность пользовательского сценария.
- Управляй SEO-метаданными через единый сервис уровня приложения на основе Angular `Title` и `Meta`, не дублируй работу с метатегами в компонентах.
- Метаданные маршрута задавай декларативно рядом с конфигурацией маршрута или формируй через resolver/facade для динамических сущностей.
- Публичные индексируемые страницы должны корректно отдаваться при прямом открытии URL и быть пригодны для SSR или prerender.

## NestJS

- Для обычных class-provider зависимостей используй constructor injection без `@Inject()`: `constructor(private readonly service: Service) {}`.
- Используй `@Inject()` только когда токен нельзя однозначно получить из runtime-типа: для строковых и `Symbol`-токенов, интерфейсов, кастомных provider-токенов, `forwardRef` и других специальных случаев.
- Constructor parameter properties NestJS являются допустимым исключением из общего правила о приватных полях через `#`: для внедряемых зависимостей предпочитай идиоматичный `private readonly` в конструкторе.
- Контроллеры должны заниматься только HTTP-слоем.
- Бизнес-логику размещай в сервисах.
- Проверяй входные данные через DTO и `class-validator`.
- Не возвращай внутренние ошибки и stack trace клиенту.
- Проверяй права доступа к изменяемым сущностям.
- Новые endpoint’ы документируй через Swagger.

## Проектирование перед реализацией

- Перед изменением кода сначала определи, как ответственность должна распределяться между сущностями, компонентами и сервисами.
- Размещай данные и поведение в той сущности, которой они принадлежат по смыслу.
- Предпочитай полиморфизм и инкапсуляцию проверкам типа, большим `switch` и таблицам соответствий во внешних сервисах.
- При добавлении нового типа существующие сервисы по возможности не должны требовать изменений — соблюдай принцип Open/Closed.
- Сервисы должны координировать работу сущностей, а не содержать знания обо всех их конкретных типах.
- Не создавай feature-specific решение, если небольшая универсальная абстракция действительно пригодна для повторного использования.
- Перед созданием новой абстракции проверь существующие компоненты, сервисы, базовые классы и утилиты.
- Не вводи абстракцию ради абстракции: переиспользуемое решение должно упрощать минимум текущий сценарий и вероятные аналогичные сценарии.
- Сначала зафиксируй инварианты и владельца состояния, затем проектируй публичный интерфейс, и только после этого приступай к реализации.
- Перед написанием кода кратко сформулируй выбранное архитектурное решение и возможные компромиссы.
- Если быстрое локальное решение нарушает текущую архитектуру или потребует добавлять новые `case` при каждом расширении, остановись и выбери расширяемый вариант.

## Проектирование API

- Проектируй API resource-oriented: URI содержит существительные и идентификаторы ресурсов.
- Действие выражается HTTP-методом.
- Состояния и выборки передаются query-параметрами.
- Не используй в URI, например, get/list/create/catalog, если это не самостоятельный доменный ресурс.

## Проверка SEO

Перед завершением задачи, затрагивающей публичный интерфейс или маршруты:

Проверяй только затронутые аспекты SEO. Для чисто визуальных изменений без изменения контента, метаданных и маршрутов достаточно проверить семантику изменённой разметки; повторный аудит sitemap, robots и метаданных не нужен.

1. Определи, должна ли изменённая страница индексироваться.
2. Проверь `title`, `meta description`, canonical и robots.
3. Проверь наличие одного `h1`, иерархию заголовков и семантическую разметку.
4. Проверь `alt` изображений и наличие доступного текстового содержимого.
5. Проверь Open Graph, Twitter Card и JSON-LD, если они применимы.
6. Проверь внутренние ссылки, sitemap и редиректы при изменении маршрутов.
7. Проверь отсутствие очевидного ухудшения LCP, CLS и INP.
8. Сообщи, какие SEO-проверки выполнены и какие неприменимы.

## Проверка результата

### Временный режим экспериментальных фич

- Пока пользователь явно не отменит этот режим, считай текущую разработку фич экспериментальной.
- Для экспериментальных фич по умолчанию не добавляй новые тесты и не запускай существующие тесты, сборку, проверку типов или lint.
- Проверяй изменения просмотром diff и вручную в браузере, если он доступен; выполняй `git diff --check`.
- Автоматические проверки, кроме `git diff --check`, запускай только по явной просьбе пользователя. Новые тесты также добавляй только по явной просьбе.
- Если изменение затрагивает авторизацию, права доступа, пользовательские данные или миграции, сначала объясни, какая точечная проверка нужна и почему, и согласуй её с пользователем.
- Эти временные правила имеют приоритет над остальными указаниями этого файла о добавлении тестов и запуске проверок, включая `yarn lint:workspace`. Существующие тесты не удаляй.

### Обычный режим

Следующие правила применяются вне экспериментального режима, а в экспериментальном — при выборе объёма явно запрошенных проверок.

Выбирай минимальный достаточный набор проверок по риску изменения, а не запускай весь набор автоматически:

- Документация и инструкции: просмотр diff и `git diff --check`; без сборки, lint и тестов.
- Стили и небольшая вёрстка без изменения поведения: просмотр затронутого экрана, если браузер доступен, и `git diff --check`. Для изменённых Angular-шаблонов при необходимости используй одну проверку компиляции. Не создавай unit-тесты для отступов, цветов и статической разметки.
- Логика, состояние, API: запускай существующие тесты только затронутого поведения. Добавляй тесты для существенной новой логики или регрессии, если существующих проверок недостаточно.
- Сборку приложения запускай при изменении сборочной конфигурации, зависимостей, публичных контрактов между проектами или когда точечные проверки не подтверждают компиляцию. Не дублируй её отдельной проверкой типов без причины.
- Lint ограничивай изменёнными файлами или проектами. Полные проверки workspace — только по явной просьбе, перед релизом или при изменениях, влияющих на весь workspace.
- Интеграционные тесты с БД нужны для изменения запросов, транзакций и прав доступа; не запускай их для визуальных правок.
- Не повторяй успешную проверку, если после неё не изменился проверяемый код. После исправления ошибки повторяй только упавшую и непосредственно затронутые проверки.
- Не расширяй проверки на соседние подсистемы без обнаруженной проблемы. Известные предупреждения вне задачи не являются поводом для дополнительных проверок.
- Если браузер или инструмент недоступен, кратко сообщи об этом; не компенсируй визуальную проверку серией нерелевантных тестов.
- Перед завершением выполни `git diff --check` и кратко сообщи результат реально выполненных проверок и существенные ограничения.
