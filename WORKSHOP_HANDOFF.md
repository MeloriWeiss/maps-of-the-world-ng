# Workshop: resume implementation

## Последние изменения: сохранение и запуск API (2026-10-11)

Пользователь подтвердил, что пакетная загрузка обзорных тайлов сократила число HTTP-запросов. Затем выяснилось, что долгий Save создавал много внутренних запросов к БД: `stageBundle` прежде вызывал отдельную транзакцию для каждой страницы и каждого PNG и последовательно отправлял PNG в object storage. Теперь в `MapSceneV4Service` страницы staging записываются группами до 24, PNG — группами до 8; внутри группы не более четырёх одновременных `storage.put`. Проверка содержимого и координат выполняется до записи. Каждая группа заменяет совпадающие ключи атомарно, поэтому повтор bundle продолжает работать; ключи заменённых PNG ставятся в очередь очистки в той же транзакции. В `MapSceneCommitService` при повторном сохранении опубликованные тайлы обновляются группами до 100 вместо `findUnique`/`upsert` на каждый тайл. При первой публикации остаётся уже существующий `createMany`. Формат данных и миграции не менялись. Реальное ускорение пока не измерено; подготовка PNG в браузере также занимает время, поэтому оценивать отдельно длительность `PUT .../bundle` и `PATCH .../scene-commits/:id`.

На фронте завершённое действие ставится в асинхронную очередь журнала IndexedDB; полный локальный черновик обновляется с задержкой 250 мс. Перед отправкой Save ждёт `journal.flush()`. Промежуточные кадры движения указателя отдельно не записываются. Это не означает синхронную запись каждого пикселя.

Автоперезапуск стандартного `nx serve api` зависит от Nx daemon, поскольку `api:build` использует `nx:run-commands`; при пропаже daemon сервер мог продолжать работать со старым `dist`. По просьбе пользователя **старый `yarn start:api` оставлен без изменения**. Добавлена отдельная команда `yarn start:api:webpack-watch` → `api:serve-webpack-watch` → `tools/scripts/serve-api.cjs`: Webpack сам следит за исходниками, после успешной сборки перезапускает Node, а при ошибке останавливает старый процесс. Скрипт также выполняет прежние deploy миграций и generate Prisma перед dev-запуском. Для использования новой команды требуется остановить текущий API и запустить её отдельно. Production build и `api:serve:production` не менялись.

Изменения просмотрены по diff; `git diff --check` прошёл. По просьбе пользователя сборка, тесты, typecheck, lint и проверка автоперезапуска не запускались. При следующем ручном запуске проверить успешную сборку, изменение исходника API и новый старт процесса; при большом Save сравнить время `PUT bundle` и `PATCH publish` и проверить повторную загрузку карты.

## Пакетная загрузка обзорных тайлов (2026-10-11)

Для просмотра добавлен `GET /maps/:id/tile-packs/:level/:x/:y?revision=...&mask=...`: один запрос содержит до четырёх соседних PNG (2×2) в компактном бинарном формате: число тайлов UInt32LE, затем для каждого x/y Int32LE, version/length UInt32LE и исходные PNG bytes. Маска 1–15 указывает только действительно нужные позиции, чтобы на краю экрана не читать лишние PNG из хранилища. Сервер проверяет доступ и revision один раз и читает запрошенные PNG параллельно; изображения не пересчитываются и не увеличиваются. Клиент использует пакеты для bootstrap и видимого обзора, не более двух запросов одновременно; сохраняет каждый PNG в прежнем кеше, помечает отсутствующие тайлы и игнорирует ответы старой revision. Старые одиночные tile GET и inventory остаются для подготовки сохранения. Геометрия по-прежнему приходит отдельно пачками до 24 страниц. Число HTTP запросов на типичный экран с 16 тайлами должно снизиться примерно с 16 PNG + inventory до 4 пакетов; число чтений из object storage останется примерно тем же. Сборку и тесты по просьбе пользователя не запускали, нужен ручной просмотр Network при открытии/зуме и после Save.

## Сетка под объектами и запросы при зуме (2026-10-11)

Готовые дочерние обзорные тайлы очищают родительский тайл под собой, чтобы не оставлять двойные контуры после перехода между уровнями.

Рендер теперь очищает кадр, рисует обзорные и локальные тайлы с фигурами, затем одной операцией `destination-over` рисует сетку и фон. Локальные тайлы больше не содержат отдельную сетку или фон. Готовый локальный тайл очищает под собой обзорное превью, чтобы одна и та же фигура не рисовалась дважды с небольшим сдвигом краёв: именно это давало ореол после Save. При загрузке полностью непрозрачного обзорного PNG клиент один раз делает пиксели, точно совпадающие с цветом фона карты, прозрачными; уже прозрачные PNG не обрабатываются. К только что подготовленным PNG после Save эта обработка не применяется. Новый Save не требуется. Активный путь сохранения уже создаёт прозрачные превью версии 3. Подготовительный `ScenePreviewBuilder` тоже переведён на прозрачный фон перед будущим подключением. У сгенерированных рек убрана непрозрачность 0.9; континенты уже имели opacity 1. Для существующих пользовательских фигур заданная им непрозрачность сохраняется.

Запросы обзорных тайлов запускаются через задержку 120 мс после смены уровня или набора видимых тайлов, чтобы быстрый зум не отправлял запросы для промежуточных масштабов. Ограничения параллелизма 4 inventory и 6 PNG остались. Уже отправленные запросы не отменяются; это возможный следующий шаг, если после ручного просмотра их всё ещё слишком много. Геометрия сохраняется в мировых координатах из `exportShapes()`, разбиение по страницам использует bounds только для индексации, а `restoreSerializedShape()` возвращает те же x/y и points. После Save камера и масштаб могут измениться, но координаты фигур не пересчитываются. Сборка, тесты и браузерная проверка не запускались по просьбе пользователя.

При переполнении удаляет старейшие ожидающие и завершает их `result$` со значением `undefined`; `ReplaySubject(1)` сохраняет результат для подписки после удаления. ## После Save сетка поверх фигур и лишние запросы чанков (2026-10-11)

До первого Save сцена живёт целиком в памяти и `ChunkRenderer` рисует геометрию без HTTP. После Save появляется серверный header/revision; при повторном открытии видимая геометрия загружается страницами. Это нужно для больших карт, но низкий zoom ошибочно запускал загрузку страниц: `#forceDetails` оставался включённым после revision 0, а условие остановки требовало уже загруженный preview tile. Теперь после публикации `#forceDetails` сбрасывается, а при удалённом масштабе клиент запрашивает только тайлы превью; детальные страницы запрашиваются при приближении или явном `loadViewportDetails()`. При первой публикации без source map клиент сохраняет покрытие уже находящейся в памяти сцены, поэтому прямо после Save продолжает рисовать её тем же геометрическим путём и не делает повторную загрузку собственных страниц.

Сетка была под локальной геометрией, но поверх непрозрачных сохранённых превью. Превью нового формата (`previewContentVersion: 2`) имеют прозрачный фон; общий фон и сетка рисуются до них, а локальные растровые тайлы сохраняют прежний порядок «сетка → фигуры». Старые версии 0/1 пересоздаются при следующем Save без правки фигур. Сразу после обновления web карта со старым превью ещё может скрывать сетку до этого Save. Браузерная проверка, сборка и тесты не запускались по просьбе пользователя.

## Визуальная регрессия после сохранения (2026-10-11)

Первый Save карты 43 прошёл, но после него дома и мебель стали видны на масштабе мира, сетка исчезала на превью, а часть чанков выглядела размытой. Причины: `#preparePreviewTiles` рисовал все фигуры в листьях без `minZoom`, затем уменьшал эти изображения в родителей; `drawOverview` одновременно рисовал слишком мелкие уровни; сетка рисовалась до непрозрачного превью; отсутствие `bootstrap` ошибочно включало загрузку геометрии даже на отдалённом масштабе.

Исправлено: постоянное превью содержит только фигуры, видимые на всех масштабах (`minZoom <= 0`); детали с порогом масштаба рисуются геометрией при приближении. Родители по-прежнему собираются из дочерних тайлов, чтобы не терять не загруженные клиентом соседние области. Клиент выбирает уровень превью по масштабу, выравнивает края по пикселям и рисует сетку после превью в ещё не готовых областях либо внутри готового геометрического тайла. Автоматическая детальная загрузка на удалённом масштабе больше не включается лишь из-за пустого `bootstrap`.

В заголовок карты добавлен необязательный `previewContentVersion: 1`. При следующем Save старой карты клиент один раз загружает её страницы и пересоздаёт превью даже без изменений фигур; для уже сохранённой карты 43 нужен повторный Save после обновления web. Это восстановление пока ограничено существующим пределом `#discover` в 1024 страницы и ещё не проверено в браузере. Тесты и сборку не запускали по просьбе пользователя; нужен ручной просмотр карты после Save и reload.

## Автоматический перезапуск API (2026-10-11)

`nx serve api` уже следит за изменениями и перезапускает процесс после сборки. Однако при изменении он запускает `nx run api:build:development` отдельным процессом, поэтому флаг `--skip-nx-cache` у `nx serve` не гарантировал пересборку: вложенная команда могла снова взять старый `dist` из кэша. Для target `api:build` в `apps/api/project.json` установлен `cache: false`, а лишний флаг удалён из `start:api`. Теперь каждый запуск сборки API, включая автоматические после изменения исходников, должен создавать новый JS. После изменения конфигурации нужен один перезапуск текущего `yarn start:api`; далее изменения должны подхватываться автоматически при работающем Nx daemon. Сборка и ручная проверка перезапуска пока не выполнялись по просьбе пользователя; приведённое ниже старое описание `--skip-nx-cache` больше не актуально.

## Активный Save: один бинарный upload и однократное превью (2026-10-11)

Кнопка Save теперь использует существующий staged commit, но загружает все подготовленные страницы и PNG **одним** `PUT /maps/:id/scene-commits/:commitId/bundle`. Пакет состоит из ограниченных кадров `WMSAVE1`, с SHA-256 каждого payload, цепочкой хешей и обязательным terminal/EOF.
